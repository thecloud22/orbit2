# Orbit 2.1 — Understand a complex SOP before drafting it

**Status:** Planning document. Nothing here is built.

**Date:** 2026-09-22

**Builds on:** Orbit 2.0 (this repository, specified in `docs/orbit-2.0-functional-specification.md`). 2.1 adds a
front end to how a procedure comes in; it assumes 2.0's workflow, run, evidence and practice-copy
capabilities exist and changes none of them. Like the 2.0 spec, this plan states product behaviour
and leaves technology open.

**Design canvas:** "Orbit 2.0 — Slice 1 screens", row *Orbit 2.1 — understanding a long procedure
(proposed)*.

---

## 0. The problem

Orbit's path from a document to a workflow asks one model call to produce a complete, valid
workflow of screen-level steps (open, enter, activate, read). Real SOPs are written as goals
("verify eligibility", "escalate a disputed claim"). They mix rules, background, hand-offs and
actions Orbit must not take, and they often state policy as tables. Forcing all of that into one
valid workflow makes the model either refuse or invent screen detail the document never gave it.
The invented version still passes validation, which makes it the dangerous case.

## 1. The flow

```text
 Your procedure (pasted or PDF, any length)
        │
        ▼
 ① SORT             Orbit splits the text into sentences. A model labels each one
   Orbit + model     by its number. It cannot add, skip, merge or rewrite a sentence.
        │
        │   Task · Rule · For a person · Background · Orbit won't
        ▼
 ② CONFIRM          A person fixes labels, merges or splits tasks, corrects rule tables.
   person
        │
        ▼
 ③ SKELETON         No model. Tasks become placeholders, rule tables become branch steps,
   Orbit             person items become hand-offs, outcomes become endings.
        │
        ▼
 ④ CONNECT          Orbit works through the tasks itself on the practice copy, in order,
   Orbit, asks       once per example. A person answers questions against a picture, and
   if unsure         demonstrates only when Orbit finds nothing, starting from that point.
        │
        ▼
 Publish → run → evidence        (2.0, unchanged)
```

## 2. Principles

- **The model labels; it never writes structure.** Orbit segments the text. The model returns one
  label per sentence number, so it cannot skip or invent content.
- **Nothing is dropped silently.** Every sentence ends with exactly one label. Coverage is counted
  from the labels, not estimated.
- **Screen detail comes from the application, never from the document.** The document says what a
  task is for. Orbit finds out how it is done by working through the practice copy.
- **Rules stay comparisons.** A rule table runs as a chain of comparisons between values the
  application shows. It has no arithmetic and no "or" within a row, and every compared value must
  be read by some task. The table is a review surface, not a new execution capability.
- **Partial automation is a normal result.** A version that automates three tasks and hands two to
  people publishes. It is not a failure.

## 3. Connecting a task (step ④)

A person demonstrating every task does not scale, and it breaks down worst in the middle of a
process: to reach task 5 someone has to do tasks 1–4 first, often on a record in a particular
state. So in 2.1 **Orbit connects tasks itself**, and a person is asked only when Orbit is unsure.

**How Orbit reaches a task partway through.** Connection runs in one continuous session on the
practice copy, in task order. Tasks that are already connected are repeated to reach the state the
next task needs. Nobody redoes earlier work to get Orbit to task 5.

**How it reaches every branch.** The author gives one example per ending (for instance: a claim
that is found, one that does not exist, one that is closed). Each example is run through the tasks,
and each ending's branch is connected in the state that example produces. An ending no example
reaches is reported as *"no example reaches this"* along with the condition it needs, so the author
knows exactly what kind of record to supply.

**When Orbit asks.** Orbit asks only when it has a structural reason to doubt. It never uses a
confidence score.

| On the page, for this part of the task | Orbit |
|---|---|
| Exactly one thing matches the task's wording, or only one thing of the right kind | Connects it without asking, and marks it so |
| Several plausible matches | Asks, showing a picture with the candidates numbered |
| Nothing matches | Asks. The person can point at it, say it is not on this page, or show just this task |
| An action whose effect is unknown | Asks whether it changes anything, *before* doing it |

**When a person demonstrates.** Only as a fallback for one task at a time. The browser opens at the
point Orbit reached, with earlier tasks already done, and the person shows only that task.

**When replay works.** Replay reaches a task partway through only if repeating the earlier tasks
is harmless:

| Earlier tasks | Replay | What Orbit does |
|---|---|---|
| Only read (search, open, read) | Safe, as often as needed | The normal case |
| Change data | Would submit twice | Start that example from a record already in the needed state, or reset the practice copy between passes |
| Wait on time or people (an approval, an overnight batch) | The state cannot be recreated | Hand the task off, or take over from a live session. **Not designed yet.** |

**Limits.** Connection uses only the practice copy's addresses and only the example values the
author supplied. It never performs an action a person has not confirmed as read-only. A task that
comes after a state-changing action is either connected on the practice copy under 2.0's rules for
consequential steps or handed to a person.

## 4. What Orbit holds (product terms)

| Thing | What it records |
|---|---|
| Sentence | Its text, where it sits in the document (page, section) and its position. Fixed once the document is in. |
| Label | Exactly one per sentence: task, rule, for a person, background, or won't. Records the reason and whether the document stated it or Orbit inferred it. |
| Task | A goal-level title ("Find the claim"), the application, who does it (Orbit or a person), the values it reads and produces, and the sentences it came from. |
| Rule table | The question it answers, its columns (named values), its rows (conditions and then-what), its default, and the sentences it came from. |
| Ending | A named conclusion and the values it publishes. |
| Example | A value set supplied by the author, the ending it is meant to reach, and whether it reached it. |
| Coverage | Counted: sentences per label, tasks connected, endings reached. |

The understanding is kept with the workflow version as evidence, so an auditor can see which
sentence became which step and which sentences were deliberately left to people.

## 5. Screens (on the canvas)

| Screen | Behaviour |
|---|---|
| Bring in a procedure | Accepts pasted text or a PDF of any length. Lists four stages. If part of the procedure cannot be automated, that part is kept and routed to a person. The draft stops only for a sentence Orbit cannot place, and Orbit names that sentence. |
| **What Orbit understood** | The document with every sentence labelled, a coverage bar ("12 of 12 placed"), and a panel for relabelling a sentence. Outstanding questions block confirmation. |
| **The rules, as tables** | Each rule as a table beside its source sentences. Warns when a column is a value no task reads, and offers three resolutions: a task reads it, a person checks it, or drop the condition. Shows the comparison chain the table runs as. |
| **Orbit connects each task** | Examples per ending, each marked reached or not reached. Tasks in order, each marked *connected without asking*, *question*, or *hand off*. The current question is shown against a picture of the page. A fallback, "show just this task", starts from where Orbit is. Publish stays disabled until every question is answered and every ending is reached. |
| Check the draft | Steps grouped under their task. |

## 6. Acceptance criteria

1. Every sentence of an uploaded or pasted procedure receives exactly one label. A result that
   leaves a sentence unlabelled, or labels one twice, is rejected before a person sees it.
2. No step's screen detail comes from the document's text.
3. A task that only occurs partway through a process is connected without a person repeating the
   earlier tasks.
4. Every ending is either reached by an example or reported as unreached, with the condition it
   needs.
5. A rule that compares a value no task reads cannot be confirmed.
6. A published version records its coverage: tasks Orbit does, rules it decides, hand-offs, and
   items left to people on purpose. Each run's evidence lists the items left to people.
7. When someone does demonstrate a task, the session starts at the point Orbit reached, and they
   demonstrate only that task.

## 7. Delivery slices

| Slice | Delivers |
|---|---|
| 2.1-a | Sentence segmentation and the five labels; the coverage count; rejection of skipped, duplicated or invented sentences. |
| 2.1-b | The sort step against a model, one section at a time for long documents, with one repair attempt; the "What Orbit understood" screen, read-only first. |
| 2.1-c | Confirming and editing: relabel, merge or split tasks, questions. |
| 2.1-d | Rule tables: review, the "a value nothing reads" check, and compiling a table to a comparison chain. |
| 2.1-e | The skeleton: tasks to placeholders; a version cannot publish with a placeholder still unconnected. |
| 2.1-f | Connecting tasks on the practice copy: examples per ending, repeating earlier tasks to reach state, structural questions, and the one-task demonstration fallback. |
| 2.1-g | Coverage on the published version and in each run's evidence. |
| 2.1-h | An evaluation set of 5–10 redacted real SOPs with hand-assigned labels, reporting agreement. Runs against a real model only on explicit request. |

Order: a → b → h (to learn early whether the labels are good), then c → d → e → f → g.

## 8. Open questions

1. **Can the practice copy supply every example?** An ending may need a record in a state the
   practice copy does not contain (for example, a claim over $10,000 and older than 90 days). The
   options are that the author creates one, that the ending is connected by demonstration only, or
   that it ships as a hand-off until an example exists.
2. **Task granularity.** Different models split the same procedure into 3 tasks or into 12. Is
   merge/split on the confirm screen enough, or does Orbit need a stated rule (one task per
   application screen visit, for example)?
3. **Short procedures.** Should a short pasted procedure skip the sort step and use 2.0's direct
   path?
4. **Procedures that reference other procedures** ("see CL-07"). For now they are labelled
   background. Should 2.1 offer to bring the referenced procedure in?

## 9. Risks

- **Label quality on real documents** is the main unknown, which is why 2.1-h runs early. If
  agreement is poor, the confirm screen carries more of the load. That is acceptable. Silent errors
  are not, and the sentence-number design prevents them.
- **Scope creep toward an autonomous agent.** The skeleton step is deterministic and closed, and
  connection acts only on confirmed steps with the author's example values, on the practice copy.
  Neither may grow a path that acts on its own judgement.

## 10. Data between tasks and large tables

These rules match 2.0's. They're restated here because a long procedure passes far more values
than a short one does. The canvas shows them on "What moves between tasks" and "Large tables".

**Values between tasks.**

- A task passes the next task named, typed values, never a page. The types are text, money, date,
  whole number, yes/no, secret, and table.
- A value may be used only after a task has produced it, on every path that reaches that use.
  Otherwise the version cannot publish. Sorting fills in each task's reads and produces, and
  connecting confirms where each one is read from on the page.
- Values move whole. There is no joining of values and no arithmetic, so a total must be one the
  application shows.
- A secret is typed into one field and goes nowhere else. It is required at every run, never
  carried on to another task, and never stored.
- A run's record shows each value's origin (task, page, part of the page) and every place it was
  used. The same holds when a value read in one application is typed into another.

**Large tables.**

- A table is never a value. It can be repeated over (`for each`) or downloaded, and it is never
  typed into a field, added up, counted, joined, or filtered by a formula. Filtering is done with
  the application's own filters, as a task.
- A collect has a page ceiling and a row ceiling, both fixed at publication. A run that exceeds
  either one stops and says so. It never stores a table with the end cut off. Columns are found by
  their heading, and blanks that were seen are counted.
- In `for each`, every row gets its own record (values and ending). Pictures are kept only for rows
  that stop or are handed to a person. A run that stops at row 412 resumes from row 412.
- Size tiers: up to a few thousand rows, collect from the screen. Tens of thousands, use the
  application's own export or its API. Beyond that, the job is a data integration, not an Orbit
  workflow.

**Volume and retention (open).** Connecting keeps only the pictures behind questions and the page
match for each step. Replay passes that raised no question are discarded. Runs keep the record
(values, comparisons, ending, version) for a long period, and pictures for a set retention period.
Traces are kept only on failure. Redacting pictures and snapshots that contain customer data is a
2.1 requirement, not later work.

## 11. The InMem

Every run has one **InMem**: a single container for all the data the run touches. Tasks never
pass values directly to each other. Each task writes what it found into the InMem, and anything
later (tasks, rules, the ending, a person in Runs, an auditor) reads from it. It holds the data and
it is the record, so the two can never disagree.

**Sections.** Given (run inputs), Found (values tasks read), Decided (what each rule table
concluded, with both values of every comparison), Tables (collected tables), Handed over (questions
put to people, and their answers), Conclusion (the ending and the values it publishes).

**Properties, each enforced:**

1. **One per run.** Each row of a `for each` gets its own page within that run's InMem.
2. **Written once.** An entry is never changed. A correction is a new entry that points at the
   one it corrects.
3. **Every entry has a source:** the task, the part of the page, and the time.
4. **Its shape comes from the version.** A published version declares what its InMem may
   hold, and nothing else can be written. "Used before it was made" becomes "read from the InMem before
   anything wrote it", which is checked at publish.
5. **Secrets are only noted.** The InMem records that a secret was given, never the value.
6. **Entries outlast pictures.** Screenshots expire after their retention period, while the entries
   they back up are kept for the longer record retention period. This is how §10's retention split
   appears to users.

**Where it appears.** In a run, as its own screen ("A run's InMem" on the canvas), which can be
downloaded as a spreadsheet. In the draft, "Values this workflow declares" becomes "What the InMem
holds". In step 4, each example's pass produces an InMem, so the author sees exactly what
that example would record.

**Name.** Chosen 2026-09-22: **InMem**. "Case file" was rejected; "ledger" (already used across
the repo, and a real business object a workflow may read), "dossier", "folio" and others were
considered. The construct is unchanged by the name.

## 12. Changing the draft by chat

Authors can change the draft by typing a request in a small chat panel. The chat appears on the
understanding screens (steps ② and ③: sentences, rule tables, tasks) and nowhere else. It is not
a general assistant. It can change this draft and explain it, and it can do nothing else.

**What it can do.** Every change the chat makes is one edit from a closed list:

| Edit | Example request |
|---|---|
| Relabel a sentence | "Sentence 12 is for a person, not background" |
| Merge, split, rename or reorder tasks | "Tasks 2 and 3 are one screen, merge them" |
| Have a task read another value | "Task 3 also reads the claim's age, shown as Age (days)" |
| Add, change or remove a rule-table row | "Add a row: litigation claims go to Legal" |
| Hand a task or sentence to a person | "Let a person decide the call-back" |
| Add an example for an ending | "Use CL-3310 for team lead review" |
| Rename a value | "Call `outstanding` `amountOutstanding`" |
| Explain (changes nothing) | "Why is sentence 9 for a person?" |

**Guard rails.** Orbit enforces each of these. None of them relies on the model following its
instructions: the model only proposes, and Orbit decides what is allowed.

1. **Closed edit list.** The model returns edits from the list above, or an explanation. Anything
   else is discarded, and the author sees "Orbit can't make that change here".
2. **Only this workflow's applications.** Any edit or request that names an application or web
   address is checked against the applications this workflow may open. An administrator sets that
   list; the chat cannot add to it. "Look up the price on Amazon" is refused. The refusal names the
   applications that are allowed and points to Admin. The address check also runs **before** the
   message reaches the model, so an address outside the list is never sent.
3. **Nothing that changes data.** No edit may add an action that changes an application's data:
   buy, pay, submit, send, update, delete. Instead the chat offers to hand that work to a person,
   the same outcome the sort step gives an "Orbit won't" sentence.
4. **Only about this draft.** A request that is not about this draft is declined with a fixed
   message, and nothing is proposed. Examples: shopping, writing an email, general questions,
   running code, or another workflow.
5. **The procedure stays the source.** An edit that departs from what the document says, such as
   a different threshold or a new condition, is marked **Not in the procedure** and cannot be
   accepted without a written reason. The coverage map shows it as an author's change, not a
   sentence.
6. **Nothing applies on its own.** Each proposal shows a before and after, and the sentences it
   touches. Only the author's Accept applies it. Before Accept is enabled, the proposal passes the
   same checks as publishing: no value used before it is made, and no rule comparing a value that
   no task reads. A proposal that fails a check cannot be accepted, and the chat shows why.
7. **No secrets.** A message that looks like a password, card number or account credential is
   blocked before it is sent or stored.
8. **It cannot act.** The chat cannot connect tasks (step ④), start a run, drive the practice
   copy, or publish. Those stay buttons. If an accepted edit touches a task that is already
   connected, that task goes back to "needs connecting".
9. **Recorded.** Every message, proposal, refusal and acceptance is kept in the draft's history,
   and in the audit of the version published from it.
10. **Limits.** Each workspace has a set number of messages per draft per day, charged to the
    workspace's model budget. When the limit is reached, the chat says so and editing by hand
    continues to work.

**Acceptance criteria.**
- "Find the cheapest windscreen on Amazon" returns the refusal message. Nothing is proposed, and
  no address outside the list reaches the model.
- "Update the enquiry log when done" proposes nothing that changes data. It offers a hand-off.
- "Raise the threshold to 15,000" produces a proposal marked Not in the procedure, and Accept
  stays disabled until a reason is entered.
- A proposal that would compare a value no task reads cannot be accepted.
- The whole conversation appears in the draft's history and in the published version's audit.

**Drafting only.** The chat exists only while an agent is being drafted. Publishing closes it,
and the conversation is kept with the version's audit, where it can be read but not continued. A
published version, Runs, Home, Admin and Audit never have a chat. To change a published agent, an
author starts a new draft, which opens a new chat while the published version stays as it is.
