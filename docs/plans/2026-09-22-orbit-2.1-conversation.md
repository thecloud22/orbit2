This is a record of the conversation that produced the Orbit 2.1 plan
(`2026-09-22-orbit-2.1-procedure-model.md`) and the 2.1 rows on the design canvas
("Orbit 2.0 — Slice 1 screens", https://claude.ai/artifact/HUjxQph8pGMUouJ1ULaDxE).

Your messages are quoted exactly. Claude's replies are condensed to their substance.

## 1. "Is our architecture right? The SOPs are complex, written in human language."

**Answer:** the layers are mostly right; the weak point is the first step, turning SOP text into a graph.

What holds up:
- The business rule is kept separate from the page detail that carries it out (Orbit 1.0's ADR-002/018/045).
- Versions are immutable, runs behave the same every time, and evidence is part of the product.
- The system refuses rather than guesses, and a model only ever chooses from a list a person wrote.
- Ingestion keeps its uncertainty visible: citations, assumptions, flags, questions.

What breaks on real SOPs:
1. **The SOP Graph works at the wrong level of detail.** Its step kinds (`navigate`, `fill`,
   `click`, `extract`) are screen actions. Real SOPs are written as goals, so the model has to
   invent screen detail the document never gave.
2. **One model call has to produce a complete, valid graph.** Long SOPs contain loops, hand-offs,
   waits, references to other SOPs, tables, "use judgment", and actions Orbit must not take. The
   model either refuses, or forces the text into something that passes validation, which is the
   dangerous case.
3. **Nothing accounts for what can't be automated.** Most complex SOPs are 30–60% automatable.
4. **Rules arrive as chains of yes/no decisions**, when policy is usually written, and reviewed, as
   a table.

**Proposal:** add a layer between the text and the graph: a procedure model of goal-level tasks,
rule tables, actors, and a coverage map covering every sentence. Screen detail moves to the step
where each task is connected to the application.

## 2. "How will you do what you recommend? Write a plan, update the canvas to depict the UX change, and give me a simplified flow diagram."

- **Plan:** written to `docs/tasks/plans/` in the Orbit 1.0 repository. It was later rewritten as the 2.1 plan.
- **Canvas:** a new row with these boards:
  - *How a long procedure comes in* (the flow diagram)
  - *What Orbit understood* (every sentence labelled, with a coverage bar)
  - *The rules, as tables* (with a warning when a rule compares a value no task reads)
  - a task-list board
- **"Bring in a procedure" screen:** updated to accept a PDF and to show four stages.

The flow:

```text
 Your procedure (pasted or PDF, any length)
   ① SORT       Orbit splits the text into sentences; a model labels each one by its number
                (task · rule · for a person · background · Orbit won't). It cannot add, skip, or rewrite a sentence.
   ② CONFIRM    a person fixes labels, merges or splits tasks, and corrects rule tables
   ③ SKELETON   no model involved: tasks become placeholders, rule tables become branch steps, person items become hand-offs
   ④ CONNECT    tasks are connected to the application (see §4 below)
   Publish → run → evidence   (unchanged)
```

## 3. "We are doing 2.0 — that is redo.md. I will remove it from here. Make this Orbit 2.1 and go from there. So you want the user to show every step? That is going to be difficult, especially if the step is in the middle of a process."

Agreed, and the first draft was wrong about this. Orbit 1.0's ADR-042 already establishes that **Orbit connects
a process itself** on the practice copy and asks a person only when it is unsure. Step 4 was
rewritten to follow that:

- Orbit works through the tasks in order on the practice copy, once per **example**. There is one
  example record for each ending: found, not found, closed, and so on.
- It asks only when something structural is uncertain: several plausible matches, no match at all,
  or an action whose effect is unknown. It never uses a confidence score. The person answers by
  looking at a picture of the page; they never drive the browser.
- A person demonstrates a task only as a fallback, one task at a time, starting from the point
  Orbit has reached.

The plan was renamed `2026-09-22-orbit-2.1-procedure-model.md` and rewritten in product terms on
top of 2.0, and the canvas row was retitled "Orbit 2.1".

## 4. "How about data? We may collect a lot of data. I still don't understand how step 4 works — how can we show a process in the middle after the user has done 4–5 steps?"

**How step 4 reaches the middle: replay.** Every pass starts from the beginning. Tasks that are
already connected are replayed by Orbit in seconds, so each pass gets further than the last. A pass
stops only where Orbit needs a person.

```text
Pass  Example   1 Sign in   2 Find claim   3 Read claim          Table A    Ending
 1    CL-1001   Connected   Connected      STOPS: 2 fields match  ·          ·
      ── you answer from a picture: "field 2" ──
 2    CL-1001   Replayed    Replayed       Connected              otherwise  Claim found
 3    CL-9999   Replayed    Connected      (skipped)              row 1      No such claim
 4    CL-2044   Replayed    Replayed       Replayed               row 2      Hand off
 —    (none)    ·           ·              ·                      row 3 ✗    needs an example
```

Replay only works when repeating the earlier tasks does no harm:

| Earlier tasks | Replay | What Orbit does |
|---|---|---|
| Only read | Safe | The normal case |
| Change data | Would submit twice | Start that example from a record already in the needed state, or reset the practice copy |
| Wait on time or people | Can't recreate the state | Hand the task off, or take over from a live session (not designed yet) |

**Data volume.** There are two kinds of data here:
- **Connecting a workflow:** keep only the pictures behind questions, plus the page match for
  each step. Discard replay passes that raised no question.
- **Running a workflow:** keep the record itself for a long period, keep screenshots for a set
  retention period, and keep traces only when a run fails. Redacting customer data from
  screenshots is a 2.1 requirement.

## 5. "Large tables a workflow reads, or data passed between tasks. Also, can you depict how you visualize step 4?"

Three boards were added to the canvas: *Step 4, pass by pass*, *What moves between tasks*, and
*Large tables*. The plan gained §10.

**Values between tasks:**
- Every value is named and typed.
- A value can be used only after some task has made it, on every path that reaches the use.
- Values move whole: no joining two values, and no arithmetic.
- A secret goes into one field and nowhere else.
- A table is never typed into a field.
- Every value records where it came from and where it went.

**Large tables:**
- Collecting a table has page and row limits, both fixed at publish time. If a run exceeds either,
  it stops; it never truncates the table silently.
- `for each` runs the tasks once per row, and each row gets its own small record. Screenshots are
  kept only for rows that stop.
- A long run resumes from the row where it stopped.
- A table can't be summed, counted, joined, or filtered with a formula. Use the application's own
  filters as a task instead.
- Size tiers:
  - up to a few thousand rows: read it from the screen
  - tens of thousands: use the application's export or its API
  - more than that: it is a data integration, not an Orbit workflow

## 6. "Can we create a construct for data and call it something? Like a big container to see the data."

Every run gets **one container** holding all the data that run touches. Tasks never pass values to
each other directly. They write to the container, and anything later reads from it: tasks, rules,
the ending, a person in Runs, an auditor.

- Sections: Given, Found, Decided, Tables, Handed over, Conclusion.
- Six properties:
  1. One container per run, with one page for each row of a `for each`.
  2. Written once. A correction is a new entry, never an edit.
  3. Every entry records its source.
  4. The version fixes its shape.
  5. A secret is only noted as having been given; its value is never stored.
  6. Entries are kept longer than the screenshots behind them.
- Canvas boards: *The case file* (the concept) and *A run's case file* (the screen). Plan §11.

## 12. "What is 1?" … "Ok. Call it Human in the Loop step."

Question 1 was work that waits on a person or on time ("once approved"). The first recommendation
split the workflow at the wait. Naming it a step moved it inside one workflow: the run pauses as
*Waiting for a person*, which 2.0's spec already requires and nothing in 2.0 produces yet. Tasks
after it are connected from an example already past the wait. Taking over a live session is dropped.

## 15. "Why not use chat to add more steps — is it a tech limitation or ours?"

Ours. The rule underneath is that every step has source text a person wrote, and a chat message is
such text. Chat may add steps, kept as the author's words (A.1, A.2) and marked *Written by the
author*.
